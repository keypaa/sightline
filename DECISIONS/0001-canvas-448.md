# DECISION-0001: Canvas 448x448, token count derived from config

Date: 2026-11-15
Status: accepted
Work package: WP0

## Context
M0 to M2 need a fixed image size so the visual-token count is constant. The main document requires the count to be derived, never hard-coded.

## Options considered
1. 448x448 canvas (256 merged tokens for MoonViT-V2).
2. A native-resolution or multi-resolution policy.
3. Baseten's training resolution (unknown; not stated in the paper).

## Decision
Use 448x448 for M0 to M2. Compute the visual-token count from the encoder config and canvas at load time. Resolution becomes the studied variable in M3.

## Evidence
- M0 breakdown, 2b decision 1: keep 448x448 (256 tokens) as our own choice; Baseten does not state its training resolution. [V]
- Main document section 7.1: 448x448, 16x16 = 256 tokens, count derived from the processor. [V]
- Baseten paper: training resolution not stated; interpretability images use a long side of at most 448 px. [V, via the project document]

## Consequences
The token count is constant across M0 to M2. The config stores the canvas only; `runtime.n_visual_tokens` stays `None` until the encoder is loaded. Tests assert the canvas default and that no token count is hard-coded.
